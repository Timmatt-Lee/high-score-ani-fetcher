# Repository-Specific Rules: high-score-ani-fetcher

This file defines the project-specific rules for the `high-score-ani-fetcher` repository. These rules override or extend the global rules specified in `~/.gemini/GEMINI.md`.

## 1. PR, Review & Merge Lifecycle (Custom Override)

For this repository, we enforce a Human-in-the-Loop Review process before auto-merging. Follow these steps:

1. **Local Checks:** Run all linters, formatters, and tests locally. Fix any errors.
2. **Push & PR:** Push the branch and automatically create a Pull Request.
3. **Enable Auto-Merge:** Immediately after creating the Pull Request, enable GitHub's auto-merge feature (e.g., using `gh pr merge --auto --squash` or `gh pr merge --auto --merge`) so that it automatically merges when all checks and approvals are met.
4. **Wait for Human Review:** Do NOT manually merge the PR immediately.
5. **Address & Reply to Review Comments (User-Controlled Resolution):**
   - When the user reviews the PR and leaves comments on GitHub (or notifies you in chat), you MUST inspect the GitHub comments.
   - Update the codebase to address every review comment.
   - You MUST use the GitHub API/GraphQL to reply to every comment thread on GitHub.
   - **CRITICAL:** You must NEVER resolve any comment thread. Only the USER is allowed to resolve threads.
   - If the user leaves further replies on an existing comment thread, you MUST handle and reply to them iteratively until the user is satisfied.
   - Re-run local checks and push updates to the branch.
6. **Auto-Merge on LGTM & Resolution:**
   - Before attempting any manual merge, you MUST run a GraphQL/API query on `reviewThreads` to verify that `isResolved: true` for all threads (indicating the user has resolved them).
   - Once all review comments are resolved by the user and the user has officially approved the PR (LGTM/Approved status), ensure the PR is merged (auto-merge will handle this if enabled, otherwise merge manually).
   - Delete the remote and local branches after a successful merge.

## 2. Visual / Screenshot Testing Rules (MANDATORY)

- **Strict Automated Visual Enforcement**:
  - A validator script [verify-visual-coverage.js](file:///Users/timmatt/Desktop/high-score-ani-fetcher/scripts/verify-visual-coverage.js) is configured at the root of the project to check if any UI component is missing a corresponding Storybook file.
  - This check is integrated into `npm run build`, `npm run test`, and the `.husky/pre-push` hooks. Any missing `.stories.tsx` files for a component will immediately break the build, test run, or push pipeline.
- **Comprehensive Visual Coverage**:
  - Whenever you modify styles (CSS), layouts (HTML/JSX), or interactive frontend components, you **MUST** create or update corresponding Storybook stories or visual regression tests.
  - You MUST capture every possible state of the component (such as: loading, empty, success, error, disabled, active, hover) and represent all major Critical User Journeys (CUJs).
  - Never leave any screen state unrepresented in the visual suite.
